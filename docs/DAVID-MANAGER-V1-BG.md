# DAVID Manager v1 — GitHub → Gemini → задачи за одобрение

## Какво е реализирано

DAVID Manager вече има самостоятелен **read-only инспектор** на GitHub проекти, който връща последен commit, open PR, дата на проверката и истински статус на връзката. Gemini може да предложи следващи задачи върху тази картина; ако Gemini няма ключ или не отговори, се използват консервативни правила.

Изпълнение от корена на хранилището (Node.js 22+):

- `node scripts/david-manager.cjs --no-gemini` — проверка и отчет без Gemini.
- `node scripts/david-manager.cjs` — Gemini предлага задачи, ако `GEMINI_API_KEY` е конфигуриран **само на локалната машина**.
- `node scripts/david-manager.cjs --json` — структурирана снимка за бъдещия MM Bridge.
- `node scripts/david-manager.cjs --save` — записва JSON в `.david-runtime/manager/latest-report.json`.
- `node tests/david-manager-v1.cjs` — договорни тестове без реални ключове.

По желание: `GITHUB_TOKEN` с **read-only** достъп до необходимите частни хранилища. Публичните се четат и без токен. `DAVID_GEMINI_MODEL` определя модела, ако е нужен различен от стандартния.

## Ограничения и сигурност

- Няма автоматични commits, push, merge, deploy, PowerShell, промени в Supabase или Windows действия.
- От Gemini се приемат само конкретни проектни идентификатори и типове задачи от allowlist.
- Всеки тип различен от `inspect` е **предложение, изискващо човешко одобрение**, не команда за изпълнение.
- Линк, предложен от модела, не се приема като доказателство, освен ако вече не е в проверения източник.
- Текстът от GitHub е недоверени данни, не инструкции за агента.
- `MM` е изрично `not_connected`; наличието на Bridge таблици не доказва активен pairing/worker.
- Няма достъп до работния локален DAVID JARVIS v1.1.1; кодът тук не доказва синхронизацията му.

## Следващи интеграционни стъпки

1. Сверяване на **локалната** инсталация на DAVID JARVIS с GitHub; запазване на стабилната версия и всички тайни.
2. Защитена връзка с MM Bridge с device pairing, heartbeat, audit, explicit approval/deny и ограничени действия.
3. Преобразуване на **действително одобрени** задачи към съществуващия `david_autonomous_task_v1` orchestrator; без пряк експорт на AI предложения към executor.
4. Доказуеми резултати от тестове, логове и ревизия преди маркиране на задача като завършена.
5. Пълен Windows тест с безвредна задача; едва след него — постепенно включване на автономно продължаване.

Това е **първата реална основа на DAVID като мениджър**, а не доказателство за вече работещ автономен MM–Windows цикъл.
